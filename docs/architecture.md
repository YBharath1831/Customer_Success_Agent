# Customer Success Agent: Architecture and Tuning Evidence

This document records how the ticket pipeline makes decisions and the evidence
used to tune it. Validation reports are generated by the existing
`evaluation.harness`; no separate evaluation implementation is used.

## Decision pipeline

```text
raw ticket
  -> normalization
  -> intent + urgency classification
  -> documentation retrieval
  -> deterministic routing
  -> grounded response generation
  -> guardrails
  -> auto-response, escalation, or block
```

The current router uses these signals:

1. predicted intent and the mandatory-escalation intent list;
2. intent confidence compared with `CONFIDENCE_THRESHOLD`;
3. top retrieval score compared with `RETRIEVAL_THRESHOLD`;
4. the global kill switch.

Urgency is supplied to response generation but is not currently a routing
signal. The router also does not estimate whether the retrieved passages
actually answer the ticket; semantic similarity alone is used.

## Failure analysis

### 1. Answerability is missing from routing

The router produced 17 false auto-response decisions and two false
escalations. Sixteen of the 17 false autos have
`answerable_from_docs: false` in the labelled validation data. Their top
retrieval scores still passed the `0.40` threshold because a passage can be
semantically related without answering a customer-specific question.

Examples include an unexplained invoice charge, a partially working SSO
configuration, missing webhooks, and confirmation of physical data location.
Raising or lowering a single similarity threshold cannot reliably distinguish
these from genuinely answerable tickets because their scores overlap.

The remaining false auto was a high-urgency live performance incident
(`VAL-0038`). Urgency is not currently considered by the router.

### 2. Generation contract failures dominate missed auto-responses

Generation was attempted for 63 tickets:

| Expected route | Router action | Terminal result | Count |
|---|---|---|---:|
| auto-response | auto-response | auto-response | 32 |
| auto-response | auto-response | `GenerationError` escalation | 13 |
| auto-response | auto-response | guardrail block | 1 |
| auto-response | escalation | escalation | 2 |
| escalation | auto-response | auto-response | 7 |
| escalation | auto-response | `GenerationError` escalation | 10 |
| escalation | escalation | escalation | 15 |

There were 23 `GenerationError` outcomes. Twenty-two occurred because a
passage ID listed in the structured `claims` array was absent from the
customer-facing `answer`; one response cited the ticket ID (`VAL-0056`) as if
it were a documentation passage. One additional response was blocked by the
claim-grounding guardrail.

The reported 100% citation coverage applies only to the 39 successful
auto-responses. It should not be interpreted as 100% generation reliability.

### 3. Urgency classification is biased toward medium

The urgency confusion matrix is:

| Expected | Predicted low | Predicted medium | Predicted high |
|---|---:|---:|---:|
| low (20) | 1 | 17 | 2 |
| medium (35) | 1 | 27 | 7 |
| high (25) | 0 | 18 | 7 |

Urgency requires model/data improvement before it can safely become a routing
signal. Changing its metric alone would not improve the current final decision
because routing presently uses intent confidence instead.

### 4. Retrieval is strong at document-hit level, weaker for multi-document answers

Only one applicable ticket missed every expected document, but eleven tickets
missed at least one expected document. This explains the difference between
the 98.11% hit rate and 88.68% macro recall. Chunk size, overlap, and top-k
experiments should therefore be judged using both metrics, not hit rate alone.

## Tuning order

The evidence supports this sequence:

1. improve generation format adherence through an `.env`-controlled model
   experiment, then rerun all 80 tickets;
2. add or improve an answerability signal before generation instead of using
   retrieval similarity as a proxy;
3. improve urgency training and only then assess whether high urgency should
   force escalation;
4. experiment with chunking/top-k only against the documented retrieval gaps;
5. tune confidence and retrieval thresholds last, after the missing decision
   signals and generation failures are addressed.

Each experiment must retain its configuration, run ID, reports, and before / after
metrics so the Git history shows an evidence-based improvement sequence.

## Experiment log

### Experiment 1: stronger structured-output model (invalid run)

- Run ID: `6bac1c5f-794a-4e49-88e7-41c18f924550`
- Change: `MODEL_NAME=openai/gpt-4o-mini`
- Controlled variables: classifier, index, chunking, retrieval, routing, and
  thresholds were unchanged.
- Result: OpenRouter returned HTTP `402` for all 63 attempted generations.
- Decision: reject the run as a model-quality comparison, restore the baseline
  model and reports, and do not use its 40% all-escalation result as an
  accuracy measurement.

This run demonstrates why provider failures must be separated from model
quality failures. The workflow failed safely by escalating every affected
ticket, but no conclusion about GPT-4o-mini response quality can be drawn.

### Experiment 2: conservative routing thresholds (incomplete live run)

- Run ID: `5d78dc58-d655-4f07-b135-7dc2ed020841`
- Change: `CONFIDENCE_THRESHOLD=0.83` and
  `RETRIEVAL_THRESHOLD=0.45`.
- Rebuild required: no; routing thresholds are read at application startup and
  do not change classifier or embedding artifacts.

An exhaustive counterfactual grid over the completed baseline showed:

| Configuration | Router accuracy | Final accuracy | False-auto routes | False escalations | Generation attempts | Generation errors |
|---|---:|---:|---:|---:|---:|---:|
| baseline `0.80 / 0.40` | 76.25% | 71.25% | 17 | 2 | 63 | 23 |
| candidate `0.83 / 0.45` | 78.75% | 73.75% | 11 | 6 | 53 | 19 |

The counterfactual is exact for the completed baseline responses because both
thresholds increased: every ticket that remains eligible already has an
observed generation outcome. It is still exploratory because the candidate
was selected from the validation set and can overfit that set.

The live comparison did not complete. OpenRouter latency increased sharply and
the command reached its 20-minute limit after 43 completed tickets with one
ticket in progress. No evaluation report was overwritten or accepted. The
known-good `0.80 / 0.40` runtime configuration was restored. Retry this
experiment after provider availability or quota recovers, using a longer
bounded command timeout, before adopting the candidate configuration.
